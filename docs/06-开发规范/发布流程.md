# 发布流程

> 最后验证：2026-11-12

两类发布：内部 npm 包发布（lerna）与应用服务发布。三仓服务上线的操作入口为[项目部署操作手册](../04-技术方案/项目部署操作手册.md)，本文保留发布约束和联动检查。

## 一、lerna 包发布

pay-back-core 等包发布到 taobao registry，独立版本（independent）：

```bash
pnpm version            # lerna version --no-commit-hooks：交互选版本、打 tag
pnpm publish:beta       # --force-publish --dist-tag=beta --skip-git
pnpm publish:latest     # --force-publish --skip-git
```

注意：`--force-publish` 会全量重发所有变更包；发布前确保 `pnpm build` 通过（nx 缓存命中不代表产物正确，可 `pnpm clean:dist` 后全量构建验证）。

## 二、服务上线（三仓协同）

记录 payback、payback-agent、payback-mcp 的旧/新 SHA，备份 MySQL、Agent 报告和密钥配置。在独立构建目录按锁文件安装依赖，通过 Lerna 依赖编排构建 core/server/push/client，并完成 Python 测试。

更新 MCP、Agent、push-server、server 和 client 的匹配版本，按 MySQL/Consul → push-server → Agent → server → Nginx/client 的顺序启动。MCP 是 Agent 的 stdio 子进程，更新后必须重启 Agent 才能避免继续使用旧进程。Node 使用包目录的 PM2 ecosystem；不要把 `git pull` 或替换 dist 当作已经重启服务。

上线检查清单：
- [ ] PM2 单实例、监听端口和 Consul 注册地址/环境一致
- [ ] Agent `/healthz` 正常，dry-run 可读取真实 MCP 行情，不能只看健康端点
- [ ] 后端受保护接口匿名返回 401，登录后正常；数据健康按实际交易日检查
- [ ] 登录、盯盘、复盘、聊天摘要/详情及 SSE 正常，刷新后历史可读取
- [ ] 休市过滤、core 年份覆盖、收盘双图数据条件和目标通道配置正确

回滚恢复上一发布的三个版本、匹配产物和依赖，保留数据库与报告文件后重新启动并验收；涉及 schema 变更另行恢复。不要强推分支或清空数据库。具体命令和访问边界见操作手册。

## 三、遗留自动化与容器边界

Gitee Webhook 当前仅验签、检查目标分支/目录后执行服务器 `git pull`；构建代码被注释，没有统一依赖同步、三仓发布、重启和健康检查。源码不能证明 Gitee 侧已经构建；企微 notice 只报告这段流程，不是业务上线成功凭证。当前 GitHub push 也不等于 Gitee 自动部署。

现有 Compose 仅覆盖 client/server/mysql；server 镜像 Node 16/npm、客户端 Nginx 配置及网络、Agent/MCP/push 容器缺失等差距见操作手册。修正和目标环境验收前，不以 `docker-compose up -d` 作为完整三仓生产发布方式。

## 四、发版联动检查

| 变更类型 | 上线前动作 |
|----------|-----------|
| entity 改动 | 先备份并评估存量数据影响，生产 DB_SYNCHRONIZE=false；结构变更单独制定步骤 |
| scheduler config.ts 改动 | 重启后检查初始化日志，启动流程已自动注册，无需再次请求初始化端点 |
| core 改动 | 先 `pnpm build`（server 用 lib 产物，client 用源码 alias，两端都回归） |
| env 新增 key | 更新 `.env.dev/.env.prod` 模板与 [环境配置](../04-技术方案/环境配置.md) |
| Agent/MCP 变更 | 对齐三仓 SHA、Python 锁文件、记忆库权限与代理；重启 Agent 验证 stdio 子进程 |
| 图片推送变更 | 同时更新 server/push-server/Agent，核验 resvg 原生包、中文字体及飞书上传应用权限 |
